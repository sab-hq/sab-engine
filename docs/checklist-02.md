| PD-38 | Extend `WorkflowRunClaimService` (PD-5) so `Executing` runs can be re-claimed after a lease expires — mirroring the same pattern already used for `Requested`/`Declined`/`Approved`/`Failed` `[S]` | **Surfaced by an external code review** (`docs/code-review-findings.md`) as a small, well-understood, independently-buildable piece — pulled out of PD-33's prose into its own item since it doesn't need PD-33's harder open questions resolved first, just an extension of already-completed PD-5 code. This is the literal, concrete mechanism PD-33's design depends on for detecting a crashed worker's orphaned run in the first place. Testable today against the existing Postgres claim-service test harness, zero new dependencies. | ⬜ Not Started — **the gap, precisely:** `WorkflowRunClaimService.ClaimableStates` (PD-5) currently lists `Requested`, `Declined`, `Approved`, `Failed` — `Executing` is deliberately absent, since under the original design a run in that state is assumed to be actively held by a worker. That assumption breaks the moment a worker crashes mid-run: today, a run stuck in `Executing` has no path back to being reclaimed at all, permanently. **What's needed:** add `Executing` to the claimable set, gated the same way the others already are — only claimable once `ClaimedAt` is older than the lease window, using the exact same `ExecuteUpdateAsync` atomic-claim pattern already proven correct for the other four states. No new concept required, just applying PD-5's existing mechanism to one more state. |
| PD-39 | Define the "unreachable" outcome for orphaned-run recovery — currently PD-35 only defines what happens when the target is reachable (healthy → continue, unhealthy → rollback); nothing defines what happens if it can't be reached at all | **A real gap in PD-35's design, found on review — moved ahead of it since PD-35 wasn't actually complete without this.** Unreachable and unhealthy are genuinely different situations, and conflating them is a real correctness risk, not a nitpick. | ✅ **Fully decided** (implementation lives in PD-42, not separate work — same convention as PD-40) — **the problem, stated precisely:** if the reachability check (tier 1 of PD-35's design) fails, there is no defined next step. The dangerous version of "solving" this would be to treat unreachable the same as unhealthy and trigger a rollback — but a dropped connection proves nothing about the target's actual state. A real SA who can't reconnect to a box doesn't conclude "it's broken, better undo my changes"; they don't know anything yet, and undoing real, possibly-fine changes based on zero evidence is itself a mistake. **The actual design has three outcomes, not two:** (1) reachable + `validate` healthy → continue/retry remaining steps; (2) reachable + `validate` unhealthy → rollback, scoped per PD-36; (3) **unreachable → conclude nothing.** Leave the run retryable — PD-38's lease-expiry re-claim already provides this for free, so "do nothing decisive yet" needs no new machinery, just *not* forcing branch (1) or (2) when the evidence for either doesn't exist. **The retry-cap sub-question is now decided:** escalate to a human via the approval UI (PD-30) after 3 consecutive unreachable reclaims, rather than retrying silently forever — infinite silent retry isn't obviously better than premature rollback, just differently wrong. This logic is implemented as part of **PD-42**, not as separate work. |
| PD-40 | Require `ExecutionResult` (Core) to be written when a step **starts**, not only when it finishes — so PD-35's "no recorded result → nothing was attempted" logic is actually correct, not just usually correct | **A real timing bug found on review in PD-35's own reasoning.** | ✅ **Decided — folded into PD-32's requirements, not separate implementation work.** PD-35 reasons "no `ExecutionResult` for `apply-patches` yet → nothing risky was attempted → just resume." That's only true if a row gets written at the *start* of a step — the naive way to build PD-32 (write only on completion) would silently break this: a crash *during* `apply-patches`, after real changes were made but before the result got persisted, would leave **no row at all**, and PD-35's logic would misread that as "never attempted." **The requirement:** insert `ExecutionResult` when a step begins (`StartedAt` set, `CompletedAt` left null), update it in place on completion — see PD-32's entry for the exact mechanics, including a real wrinkle found while verifying this against the actual entity (`Succeeded`/`Output` are currently `init`-only, not settable). |
| PD-35 | Decide whether an orphaned-run health re-check should literally invoke the `validate` module, or a lighter-weight variant | **A real prerequisite for PD-33, not a follow-up from it — moved ahead of PD-33 for that reason.** | ✅ **Fully decided** (implementation lives in PD-32/PD-42, not separate work — same convention as PD-40) — **reasoned from how real SAs/SEs actually work, not just a preference:** **(1) Reuse `validate` (PD-17) directly — no lighter-weight variant.** A real SA doesn't maintain two versions of "is this server okay" logic, one normal and one trimmed-down for recovery specifically. One trusted checklist, run whenever ground truth is needed. **(2) Sequenced as two tiers, matching how an SA actually reconnects to an interrupted box:** first, reachability alone — reuse the already-built, already-tested `WinRmExecutionConnector.HealthCheckAsync` (PD-23); only if reachable, run `validate`'s real logic. Both pieces already exist — this is a sequencing decision, not new code. **See PD-39 for what happens if reachability itself fails.** **(3) Which patches to check for is pulled from the `Plan` itself, not new bookkeeping** — the same way a real SA checks their own change record instead of guessing. **(4) "Which step did it crash during" resolves cleanly:** no recorded `ExecutionResult` for `apply-patches` → nothing risky was attempted → just resume. An `ExecutionResult` exists, complete or not → run the two-tier check first. **This specific logic requires PD-40's write-timing fix to actually be correct — now decided, see there.** |
| PD-37 | Extend `pre-flight-check` (PD-14) to snapshot which KBs are already installed at the **start** of a run, so rollback scoping (PD-36) can distinguish this run's own changes from pre-existing state `[S/M]` | **A real prerequisite for PD-36's rollback-scoping formula to actually be correct.** Positioned before PD-36 for that reason. | ⬜ Not Started — **the gap, and why it matters:** a meticulous SA never undoes state they didn't create. If a KB was already installed *before* this run ever started — unrelated history — and it happens to also appear in this run's planned patch list, blindly rolling it back on failure would undo something this run never actually touched. **What's needed:** `pre-flight-check.ps1` currently checks disk space, pending reboot, and WU service status only. Add a WUA search on `IsInstalled=1` (the same query shape `validate`, PD-17, already uses — just run *before* any changes instead of after) and record the result as a new output field, likely `InstalledPatchIds`. **A reasonable scoping call:** the snapshot likely only needs to check this run's own planned `patch_ids` (per PD-35's same reasoning), not every installed KB on the machine. **Where this needs to end up available:** the engine reads this back at rollback-decision time, from `pre-flight-check`'s own persisted `ExecutionResult`. |
| PD-36 | Design how a triggered rollback gets scoped to what's actually broken, not "everything since the start" — given `rollback-apply-patches.ps1` (PD-16) takes an explicit `PatchIds` list rather than inferring what needs undoing on its own | **A real prerequisite for PD-33, not a follow-up from it.** Depends on **PD-37** for the "before" snapshot the scoping formula needs. | ⬜ Not Started — **the actual scoping formula, reasoned from real SA practice:** don't trust `apply-patches`' own self-reported `Applied` array — a real SA checks what the target actually shows, not what an installer *said* it did. Re-verify directly against the server, reusing PD-35's same WUA-query approach. **The full formula:** rollback set = (patches this run planned to apply) ∩ (currently installed, per direct re-verification) − (already installed *before* this run started, per PD-37's snapshot). **This means structuring `WinRmExecutionSession.ExecuteAsync`'s (PD-23) flattened string output is no longer required just to make rollback scoping work** — that idea is formally parked as its own deferred item (see the Deferred table below), genuinely valuable for audit richness but no longer on any critical path. |
| PD-33 | Design crash recovery for workflow execution the way a real systems engineer would actually handle it: on finding an interrupted run, **reconnect and assess the target's actual current state before deciding anything** — not a reflexive rollback, not a blind resume | **Depends on PD-35 and PD-36 being resolved first** — the umbrella principle, not something that closes on its own. Its actual implementation is **PD-42**, not PD-32 (see the scope split below). | ⬜ Not Started — **the design, reasoned through:** (1) **Detect the orphaned run** — closed by **PD-38** (a lease-expiry check on `Executing`, not PD-32's job). (2) **Re-run a health check before deciding anything** — PD-35's job, now fully settled. (3) **Branch on the result, not the mere fact of interruption** — healthy → continue/retry (PD-35/36's `IsInstalled=0` idempotency reasoning makes this safe); unhealthy → rollback, scoped per PD-36/37; unreachable → conclude nothing, per PD-39. **The one genuinely irreducible risk:** a crash mid-install, inside a single WUA operation — an inherent Windows Update risk that exists with or without SAB. |

Either add setters to both, or reuse the exact `ExecuteUpdateAsync` pattern `WorkflowRunClaimService` (PD-5) already proved works for atomic conditional updates without needing settable properties. **Deliberately out of scope, not a gap:** crash recovery (PD-33/35/36/37/39/40) — that's PD-42, and doesn't block this item or PD-28. ## Other Known Open Threads (not yet given their own PD- entry)

- **No real module catalog loader exists.** Flagged since PD-6 — the AI agent's available-module list is still supplied manually rather than loaded automatically from an OSML checkout.
- **No workflow parser/validator exists**, unlike modules (PD-12/13) — though PD-32 will likely build at least a minimal reader as part of its own scope.
- **Wiring the AI agent to a real model** — still needs a real OpenAI/Azure OpenAI API key from Brock, deliberately not hardcoded into the repo. **Open question, not yet resolved:** does PD-28's exit test require the agent to genuinely propose the plan via a real model, or can a fixed/manual plan stand in? Worth deciding before PD-28 is attempted, not during it.
- **The approver can be shown a plan that's since been superseded.** Found in the code review (`docs/code-review-findings.md`): the decide-endpoint in `SabEngine.Api/Program.cs` re-fetches the *latest* plan for a run at decision time, rather than binding to the exact plan version the approver actually saw. Genuinely low-risk today (Phase 1 has one plan per run), but becomes a real correctness issue the moment plan revision exists (Declined → PlanDrafted → PendingApproval) — squarely PD-32/PD-42 territory. Noted here so it isn't silently forgotten by the time that matters.
