| PD-35 | Decide whether an orphaned-run health re-check should literally invoke the `validate` module, or a lighter-weight variant | **A real prerequisite for PD-33, not a follow-up from it — moved ahead of PD-33 for that reason.** Split out because it's a genuinely separate decision with its own complications. | ⬜ Not Started — **reasoning so far, leaning toward a real recommendation, not a blank question:** reusing `validate` (PD-17) directly is the more consistent, less-code answer — it's already real, tested, and lightweight (a WUA search plus basic disk/service checks), so there's no obvious need to invent a second, parallel health-check path. **But there's a real complication worth resolving deliberately:** `validate` takes an explicit `PatchIds` list to check as installed — for an orphaned-run recovery, the engine needs to know *which* patches to check for, which only makes sense if the crash happened at or after `apply-patches`. If the crash happened earlier (say, during `pre-flight-check` or `stage-patches`), running `validate` at all would be premature — nothing's been applied yet to validate. **This means PD-33's design actually needs to know which step a run crashed *during*, not just that it crashed** — which ties directly back into PD-32's plan to persist an `ExecutionResult` row per step: the last successfully-recorded row tells the recovery logic which step to resume from, and only if that's `apply-patches` or later does invoking `validate` make sense at all. Below `apply-patches`, recovery should just resume the normal step sequence, no health re-check needed first. |
| PD-36 | Design how a triggered rollback gets scoped to what's actually broken, not "everything since the start" — given `rollback-apply-patches.ps1` (PD-16) takes an explicit `PatchIds` list rather than inferring what needs undoing on its own | **A real prerequisite for PD-33, not a follow-up from it — moved ahead of PD-33 for that reason.** Split out because answering it surfaced a genuinely new, more foundational design gap worth its own attention. | ⬜ Not Started — **the real finding, worth flagging clearly:** "scoped to what's actually broken" doesn't mean `rollback-apply-patches.ps1` itself needs to get smarter — it means the *orchestration engine* needs to know exactly which KBs `apply-patches` actually succeeded on, and pass only that specific list into the rollback script, rather than naively rolling back the full original plan (which could include patches never even attempted). `apply-patches.ps1` already returns exactly this data in its structured result (an `Applied` array, per PD-16) — so the data needed already exists. **The real, more foundational gap this surfaced:** `WinRmExecutionSession.ExecuteAsync` (PD-23) currently flattens every module's structured PowerShell output (`Applied`/`Failed`/`RebootRequired` for `apply-patches`, `Confirmed`/`Missing`/`Healthy`/`Reasons` for `validate`, etc.) down into a single newline-joined **string** via `.ToString()` on each result object — the original structure is thrown away, not preserved. For the orchestration engine to reliably determine "which KBs actually got applied" (or make any other structured decision based on a module's output), it likely needs real structured data back from `ExecuteAsync`, not a flattened text blob to re-parse with string matching, which would be fragile and easy to get wrong. **This is a real design question with implications back on already-built, already-verified code (PD-23), not just new code to write** — worth deciding deliberately before PD-33 is considered settled, likely meaning `ExecutionResult.Output` becomes structured (e.g. JSON, matching each module's own `PSCustomObject` shape) rather than a plain string, or a new field is added alongside it. |
| PD-33 | Design crash recovery for workflow execution the way a real systems engineer would actually handle it: on finding an interrupted run, **reconnect and assess the target's actual current state before deciding anything** — not a reflexive rollback, not a blind resume | **Depends on PD-35 and PD-36 being resolved first** — this item's design isn't actually complete until both of its concrete sub-decisions (how the health re-check works, how rollback gets scoped) are settled; it's the umbrella principle, not something that can close on its own. Also shapes PD-32's design directly. SAB models real sysadmin practice throughout (recommend-and-approve mode, per-module rollback, health checks before *and* after patching); crash recovery should follow the same principle, not invent its own abstract logic. A controller crash and a target-server problem are different things, and treating the first as automatic grounds to act on the second is a real anti-pattern worth avoiding deliberately. | ⬜ Not Started — **the actual design, reasoned through, not just an open question:** (1) **Detect the orphaned run.** `WorkflowRunClaimService` (PD-5) currently claims `Requested`, `Declined`, `Approved`, `Failed` — **`Executing` is not in that list**, so a run whose worker died mid-execution currently has no path back to being reclaimed at all. This is a real, concrete gap PD-32 needs to close, likely a lease-expiry check on `Executing` mirroring the pattern PD-5 already uses for its other claimable states. (2) **Re-run a health check against the target before deciding anything** — essentially re-invoking `validate`-shaped logic (PD-17) as the very first thing that happens on reclaiming an orphaned run, mirroring exactly what a real engineer would do: reconnect, check what's actually true, *then* decide — the specifics of exactly which check and how are PD-35's job. (3) **Branch on that result, not on the mere fact of interruption:** target healthy → continue/retry the remaining steps (the modules are already idempotent enough for this to be safe — see the WUA `IsInstalled=0` reasoning in PD-35/36); target unhealthy → trigger rollback, scoped to whatever's actually broken (PD-36's job), not a blanket "undo everything since the start." **The one genuinely irreducible risk:** a crash happening mid-install, inside a single WUA operation — an inherent Windows Update risk that exists with or without SAB. |
| PD-32 | Wire the `OrchestrationEngine` to actually execute a workflow: read a workflow definition, call each module in order via `IExecutionConnector`, transition the `WorkflowRun` through `Executing → Completed/Failed` as it goes, and trigger a module's own rollback automatically on failure | **The single foundational gap PD-28 and PD-31 both depend on** — flagged repeatedly since PD-4, never itemized on its own until now. Placeholder entry, written with as much real detail as could be reasoned out now, so whoever picks this up isn't starting from nothing. | ⬜ Not Started — **not yet designed in code, but here's what's already known:** **What it can build on, all real and already verified:** `WorkflowRunClaimService.TryClaimNextAsync` (PD-5) already claims eligible runs atomically, including the `Approved` state — this is the natural trigger point; a background worker (likely an ASP.NET Core `BackgroundService` hosted in `SabEngine.Api`, since that's already the live host per PD-30) would poll it, and claiming an `Approved` run is what kicks this logic off. `WinRmExecutionConnector`/`WinRmExecutionSession` (PD-23–PD-27) already resolve a target, execute a module script, and return a structured `ExecutionResult` — the actual step-execution primitive already exists and is tested. `WorkflowRunStateMachine` (PD-4) already enforces the transitions this engine would drive. **Three real, unresolved sub-problems worth flagging honestly, not glossed over:** (1) **No workflow parser exists.** `patch-windows-server.yaml` (PD-21) has zero automated reader — this item will likely need to build a minimal one (deserialize the YAML into an ordered list of `module_id`/`module_version` steps) as part of its own scope, since there's nothing to execute against otherwise. (2) **Rollback script resolution is a real, concrete gap in already-built code.** `WinRmExecutionSession.ExecuteAsync` currently resolves `moduleId` → `{modulesRoot}/{moduleId}/{moduleId}.ps1` only — it has no way to invoke a module's *rollback* script, which lives under a different filename (e.g. `rollback-pre-flight-check.ps1`, per each manifest's `RollbackSpec.Procedure`, PD-12). This will need either a new parameter/overload on `ExecuteAsync`/`IExecutionSession`, or another mechanism — genuinely undecided. (3) **Scoping call on `CredentialHandleResolver` (PD-31):** this item should NOT hard-block on PD-31 — it's reasonable to build PD-32 using one connection/credential per workflow run first, and layer in PD-31's per-module tiered credentials as a refinement afterward, matching how PD-25 itself was scoped (the mechanism before the wiring). **See PD-33, PD-35, and PD-36 for related, already-reasoned-through design questions that directly shape this item** — crash recovery, the health-recheck approach, and (importantly) a likely need to change `ExecutionResult.Output` from a plain string to something structured. **Also still needed, not blocking but relevant:** persisting an `ExecutionResult` row per step (the type already exists in Core, matching Section 4.1's data model) as the engine goes, not just at the end. |

## Other Known Open Threads (not yet given their own PD- entry)

Flagged honestly across `pre-development-checklist.md`'s entries but not yet formalized as their own tracked item:

- **The real WinRM network connection is untested.** PD-23's connector code is done and verified against a substituted local session, but nobody has yet started the lab VM and confirmed it actually connects over the network (port 5985) to a real target. Worth doing deliberately, likely as part of or just before PD-28.
- **Docker sandboxing doesn't cover SAB's real modules yet.** `DockerSandboxedExecutor` (PD-27) is real and correctly isolates any PowerShell script, but the actual four patching modules are Windows-specific and won't run inside its default Linux container. Actually sandboxing them needs a Windows container image — a deliberate, disruptive Docker Desktop reconfiguration.
- **No real module catalog loader exists.** Flagged since PD-6 — the AI agent's available-module list is still supplied manually rather than loaded automatically from an OSML checkout.
- **No workflow parser/validator exists**, unlike modules (PD-12/13) — though PD-32 above will likely need to build at least a minimal reader as part of its own scope.
- **Wiring the AI agent to a real model** — still needs a real OpenAI/Azure OpenAI API key from Brock, deliberately not hardcoded into the repo. **Open question, not yet resolved:** does PD-28's exit test require the agent to genuinely propose the plan via a real model, or can a fixed/manual plan stand in for that specific test? Worth deciding before PD-28 is attempted, not during it.
